# 仓库工作流

本文档定义 Delivery System 公开仓库的分支、审查和文档边界。它适用于所有维护者与贡献者。

## 公开内容原则

本仓库是公开项目。任何被提交或推送到任意远程分支的内容，都必须能够由第三方用户、贡献者或维护者独立理解。

请勿将个人对话、临时提示词、未验证的本地规划输入、凭据、私有代码或客户资料提交到本仓库。内部协作记录应保留在本地忽略文件、私有仓库或受控的项目管理工具中。

## 分支职责

| 分支 | 用途 | 合并来源 |
|---|---|---|
| `main` | 对外官方基线与发布候选；必须保持文档完整、可审阅且不含内部记录。 | 经审查的 PR |
| `develop` | 长期集成分支；内容同样必须可公开审阅。 | 经审查的功能或修复 PR，以及来自 `main` 的同步 |
| `feature/*` | 单项功能、文档或修复的短期分支。 | 从 `develop` 创建，PR 合并回 `develop` |
| `release/*` | 版本发布、公开仓库整理或需要直接审查 `main` 的专项分支。 | 从 `main` 或明确的发布基线创建，PR 合并回 `main` |
| `hotfix/*` | 影响 `main` 的紧急修复。 | 从 `main` 创建，PR 合并回 `main`，随后同步至 `develop` |

分支名称表达工作目的，不表达个人身份或内部对话上下文。

## 日常变更流程

1. 从 `develop` 创建 `feature/<topic>`；
2. 在该分支完成一个边界清晰的改动；
3. 更新受影响的用户、维护或治理文档；
4. 执行与改动相称的校验，并在 PR 中记录未执行的验证及原因；
5. 通过 PR 合并到 `develop`；
6. 准备发布时，从 `develop` 创建或更新 `release/<version>`，再通过 PR 合并到 `main`；
7. `main` 合并后，将其同步回 `develop`，避免分支漂移。

对于只影响公开仓库规范、发布基线或默认文档的专项整理，可从 `main` 创建 `release/*` 分支并直接向 `main` 提交 PR。合并后仍须同步到 `develop`。

## Pull Request 最低要求

- 说明变更内容、动机和受影响的 Core、Adapter 或分发包；
- 使用面向第三方的文档语言，不把未完成的内部讨论当作产品承诺；
- 不提交凭据、真实用户数据、缓存或本地规划输入；
- 若修改 canonical Adapter，同步生成 `plugins/` 分发包并说明校验结果；
- 如有未运行的测试或宿主验证，明确标记为未验证，而不宣称通过；
- 合并到 `main` 前遵循 [发布前检查清单](../release/openai-codex-release-checklist.md)。
